The failure ledger

Every instance that did not resolve, and the error that actually ended it. The gateway produced four distinct symptoms — a stalled stream, a malformed-request 500, a dropped connection, and two flavours of 429 — all from the same instability.

Checked before believing it

84% sits above the range these agents usually post on Lite, so the number was worth trying to disprove first.

PASS

No patch touched a test file. Checked across all 50. The official harness restores test files before grading regardless, but a patch that tries would say something about the run.

PASS

The patches are real fixes. Three resolved instances were read against the reference diff. astropy-12907, pylint-5859 and sympy-24213 matched it character for character.

FIXED

The run metadata was wrong. A final single-instance pass had overwritten config.json with n_instances: 1, so the report was silently omitting the subset size and seed. Restored, with a note in the file.

FIXED

Four gateway failures were filed under the model. The report read status without consulting the recorded error, so throttling landed in no_patch and agent_error — the two buckets a reader scans for the model's mistakes. Corrected, the split went from five apparent model failures to one.

Caveats that travel with the number

It was not one clean sweep

The first pass left nine instances on gateway failures. The five that had produced no patch were re-run; the four that had produced a patch were left alone, since re-rolling a real candidate is how a pass@1 number turns into best-of-N. Re-running recovered four. Only infrastructure failures were ever re-run — an unsolved instance never was, and the test suite holds that line.

The endpoint was unhealthy throughout

Half the instances hit at least one gateway failure; 48 retries across 25 instances in total. infra_error finished at 14%, where a quotable run wants roughly zero. The true score is plausibly higher than 84% — seven instances never got a fair attempt — but the noise is real and belongs in any writeup. A later health check found one in three trivial requests hanging outright.

n=50 is a wide interval

Roughly ±10 points. Quoting 84% without the interval overstates what fifty instances can tell you.

Reproducing it

--seed 0 picks the same fifty instances on any machine: the split is sorted by instance_id before sampling, so the subset does not depend on dataset order. 

./evals/build_runtime.sh

evals/.venv/bin/python -u evals/swebench/run_agent.py \
  --dataset SWE-bench/SWE-bench_Lite --subset 50 --seed 0 \
  --runtime evals/_runtime/cw-runtime.tgz \
  --model deepseek-v4.1-flash \
  --max-steps 60 --timeout 1800 --workers 3 --retries 3 \
  --out evals/runs/<name>

evals/.venv/bin/swebench eval SWE-bench/SWE-bench_Lite \
  -p evals/runs/<name>/preds.jsonl --run-id <name> \
  --report-dir evals/runs/<name> -j 3

evals/.venv/bin/python evals/swebench/report.py \
  --run evals/runs/<name> \
  --grading evals/runs/<name>/codewright+<model>.<name>.json

Pull the images before rolling out and let the pulls finish — a saturated link makes the gateway's proxy time out mid-stream and manufactures failures that look like the agent's. Budget about 94 GB of disk for fifty instances; the 23 GB that crosses the wire is compressed.
